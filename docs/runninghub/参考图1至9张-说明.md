# 参考图 1~9 张可选（v1.7）

`docs/runninghub/workflows/海螺H3 人物替换专用流v1.7-可选参考图1至9张.json`
测试脚本：`docs/runninghub/test-ref-count.mjs`

## 为什么这么改

`MiniMaxH3ReferenceToVideo` 的 `ref_images` 是 autogrow 输入（`min=0, max=9`）。执行时它会遍历所有槽位：

```python
for img in (ref_images or {}).values():
    if img is None:
        continue
```

也就是说「多接一张图」是节点自己的能力，**卡点是 API**：RunningHub 的 `nodeInfoList` 只能改参数值，既不能改连线，也不能删槽位。所以“张数可选”必须在图里做成可切换的分支。

v1.5 的做法是 3 张图硬接 `ref_image_0/1/2`，数量写死。v1.7 改成：

- **9 个条件变体**：`208`（1 张）、`700~707`（2~9 张），每个变体接好对应数量的参考图槽位；
- **8 级惰性开关**：`LazySwitchKJ` 串联，`710` 选 1/2 张，`711` 选 ≤2/3 张，……，`717` 选 ≤8/9 张；
- **一个整数参数**：`736`「参考图张数（1~9）」，后面接 8 个 `张数 >= k` 判断（`750~757`，用的是 comfy-core 的 `ComfyMathExpression`，直接有 BOOL 输出），自动算出每一级开关走哪边。

`LazySwitchKJ` 的 `on_true` / `on_false` 都是 `{"lazy": True}` 且实现了 `check_lazy_status`，所以**只有被选中的那条支路会被执行**：没用到的参考图既不加载、也不编码。

`196` 的 `latent_image` 原本来自 `208` 的 LATENT 输出，改成独立的 `740 EmptyMiniMaxH3LatentAV`——否则未选中的变体不执行时会缺 latent。

## 显存：时长和分辨率是绑死的（实测）

用 14 秒的源视频（`红白膜视频.mp4`，1920×1080 / 30fps / 13.87s）在标准 24G 机器上跑，
任务 `2116822969993220098` 失败：`torch.OutOfMemoryError`，死在**二采**的采样器 `200 SamplerCustomAdvanced`。

平台给的报错原话是「VRAM OOM Alert」，建议降分辨率 / 缩短时长 / 开 Plus 大显存模式。

### 实际算出来的规格

| 环节 | 节点 | 规格 |
|---|---|---|
| 一采 | `196` + `740 EmptyMiniMaxH3LatentAV` | 960×544（`209` 选 16:9、0.5MP），长度 362 帧 |
| 二采 | `200` + `206 MinimaxH3LatentUpscaler3D` | 1344×768（`247` 二采放大像素 = 1.0MP），长度还是 362 帧 |

帧数是工作流自己算的：`286`（24fps）→ `346 VHS_VideoInfo` → `608`（+22/24 秒接续余量）
→ `193`（向上吸附到 17 的倍数）→ 13.87s 被算成 **362 帧 ≈ 15.1 秒**。

海螺 H3 是音视频一体模型，latent token 数 ∝ 帧数 × 面积：362 帧 @ 1344×768 约 36 万 token，
而工作流作者自己跑的样例只有 125 帧（5.2 秒）——**差 3 倍，24G 扛不住**。
注意这里两段采样都是 1080p 级别的输出，所以「1080p」的说法没错，错的是**帧数**。

### 对应的参数（已加进登记表，前端可直接调）

除了分辨率和时长，还有两个节点本身带的省显存开关，一起开放出来：

| 参数 | 节点 / 字段 | 默认 | 说明 |
|---|---|---|---|
| `megapixels` | `209.megapixels` | 0.5 | **一采**分辨率，0.5 ≈ 960×544，0.3 ≈ 832×480 |
| `upscale_megapixels` | `247.value` | 1 | **二采**（成片）尺寸，1 ≈ 1344×768，0.5 ≈ 960×544 |
| `video_seconds` | `286.frame_load_cap` | 5（没量到原视频时） | **输出时长（秒）**，界面是滑块（步进 0.1 秒），默认与原视频一致（服务端量了原视频时长就按它来，精确到 0.1 秒向上取整）。提交前换算成帧数：帧 = 秒 × 24（向上取整，24 是工作流 force 的固定帧率） |
| `ff_chunks` | `201.chunks` + `277.chunks` | 2 | 分块前馈的块数。**一采、二采各挂了一个**，一个参数两个节点一起改 |
| `ff_seq_threshold` | `201.seq_threshold` + `277.seq_threshold` | 4096 | token 超过它才分块；调到 2048 让它早点分 |
| `attn_head_chunks` | `202.head_chunks` | 4 | 注意力头分几组算。**只挂在二采那条链上**（`620→202→201→183→200`） |
| `upscaler_chunking` | `206.enable_chunking` | false | 二采放大时分块算，省显存、略慢 |
| `upscaler_force_unload` | `206.force_unload` | false | 放大完把模型从显存里踢掉 |
| `save_first_pass` | `271.save_output` | true | 打开后一次采样的片段也会回到我们这边（成片之外多一个文件） |

分块数、注意力分组数的方向是「越大峰值显存越低」：
`ff_chunks` 2→4→8→16、`attn_head_chunks` 4→8→16。
实测（1344×768 / 362 帧）里 16/8 反而比 2/2 快 2.9 倍——粗分块容易把 CUDA 分配顶到
「溢出到系统内存再走 PCIe」的区间，细分块全程留在显存里，所以加大分块通常既省显存又快。

### 画质档（用户不用自己研究该调哪个）

界面上多一个「画质档」下拉，选一个就一次把上面几个参数调好：

| 档 | 一采 | 二采 | 时长 | FFN 分块 / 阈值 | 注意力分组 | 放大分块 | 卸载 |
|---|---|---|---|---|---|---|---|
| 省显存（24G 保底） | 0.3MP | 0.5MP | 4 秒 | 4 / 2048 | 8 | 开 | 开 |
| 标准（24G 能跑） | 0.5MP | 1.0MP | 4 秒 | 2 / 4096 | 4 | 关 | 关 |
| 画质优先（48G+） | 0.5MP | 1.5MP | 7 秒 | 4 / 2048 | 8 | 关 | 关 |

档只覆盖「用户没自己动过」的参数（判断标准：提交上来的值和默认值不同就算动过），
所以先选档再微调某一项、或先微调再选档，结果都是对的。
实现见 `shared/runninghub.ts` 的 `RhPreset` / `rhPlan`。

跑长片只有三条路：降 `upscale_megapixels`、降 `video_seconds`、或者换「加强 48G / 旗舰 84G」机器（单价更高）。

## 轮询的一个坑（已修）

`/openapi/v2/query` 在任务失败时返回的是 **HTTP 200 + `errorCode: "805"` + `status: "FAILED"`**。
原来这里把 `errorCode` 非空一律当成接口错误抛出去，结果失败任务永远停在「进行中」，
卡片上只显示「平台暂时无法查询」，看不到 OOM 原因。

现在：查询接口带 `tolerateTaskError`，只要返回里带 `status` 就算任务结果；
失败时把 `failedReason` 里的异常类型、失败节点、平台建议一起带回来，
中文提示「显存不够（OOM）：把视频时长或成片分辨率降下来，或者换成加强 48G 机器再跑」。

## 默认值必须由我们这边兜住（画布路径的老坑）

平台保存的那份工作流里，`286.frame_load_cap = 0`（用整段视频）、`271.save_output = false`。
画布那条路只有「用户动过的」参数会带过来（`node.data.flowValues`），
没带的参数就落回平台保存的值——**一漏传 `video_seconds`（286.frame_load_cap）就又走回 OOM 那条路**。

所以 `rhPlan` 现在会先用登记表里的默认值把没带的参数补齐（枚举按标签换算成节点要的原值），
再套画质档。这样创作页和画布两条路拿到的 `nodeInfoList` 完全一致，
默认值只写在 `shared/runninghub.ts` 一处。

判据仍然是「提交上来的值 == 规则默认值 = 用户没动过」，
所以画布节点上用户手动改过的参数不会被画质档覆盖。

## 实时预览：平台这条通道走不通（已实测）

工作流里的 `337 ModelPreviewOverrideKJ` 每采样一步解码一帧，
以 `kj_preview_override` 事件推给「提交这个 prompt 的 client_id」——这是 ComfyUI 的原生 WS 通道。

**但 RunningHub 的 OpenAPI 不把它交给我们**：

| 来源 | `netWssUrl` | `clientId` |
|---|---|---|
| 提交响应 `/openapi/v2/run/workflow/{id}` | 空 | 空 |
| 查询响应 `/openapi/v2/query` | **连字段都没有** | `""` |
| 官方文档示例（`/task/openapi/create`） | `null` | 有值 |

文档自己的措辞是「❌ Avoid using `netWssUrl` as it's currently unstable; use polling endpoints instead」，
而且示例里它就是 `null`。所以这条通道在 OpenAPI 上拿不到地址，
`server/rhpreview.js` 的实时预览**在 RunningHub 上不会出帧**（代码留着，自建 ComfyUI 时能用）。

那「一次采样的结果」怎么看？只能**等任务结束一起拿**：
`271.save_output = true`（参数 `save_first_pass`，默认开）让一次采样的片段也进 `results`，
成片之外多一个文件——是完整的一段，不是实时预览。

运行中的任务也查不到半成品：`/openapi/v2/query` 在 `RUNNING` 时 `results` 是 `null`，
只有终态才带文件。

## 怎么测

```bash
export RH_API_KEY=你的key
# 先跑 3 张，确认链路通
node docs/runninghub/test-ref-count.mjs <workflowId> --count 3 --images ./refs
# 再跑 1 张和 9 张，对比产出
node docs/runninghub/test-ref-count.mjs <workflowId> --count 1,9 --images ./refs
```

脚本会：上传图片 → 提交 → 轮询 → 把结果下载到 `rh-out/ref<N>.mp4`。
`--dry` 只打印 `nodeInfoList`，不提交。

真跑之前先看一眼「这次会跑成什么样」（不提交、不花钱）：

```bash
node docs/runninghub/plan-params.mjs --preset "省显存（24G 保底）" --dry
node docs/runninghub/plan-params.mjs --max-frames 120 --ff-chunks 8 --attn-head-chunks 16 --dry
```

判定：9 张能跑完不报错、且 1 张和 9 张的产出不同 → 参数真的生效。

> 跑之前先算一下显存：`video_seconds` × `upscale_megapixels` 决定 token 数。
> 24G 机器上建议 ≤ 120 帧 × 1MP；想跑 14 秒那种长片，先降到 0.5MP 再试。
> 提交前会自动拦：「帧 × 二采百万像素」超过机器预算（24G=120 / 48G=320 / 84G 不限）直接报错，
> 提示里给出可照着调的时长、分辨率或换机器建议——实测 312 帧 × 1.0MP 在 24G 上就是
> `RuntimeError: VRAM grow failed`（节点 200 采样器，只差 420MB），平台照样扣钱。

## 已知风险

| 风险 | 说明 | 兜底 |
|---|---|---|
| `LazySwitchKJ` | 来自 KJNodes。这个工作流本来就在用 KJNodes（`ModelPreviewOverrideKJ`、`ImageBatchMulti`），大概率有 | 换成任意双分支开关，保持 `switch` / `on_true` / `on_false` 三个输入名即可 |
| `ComfyMathExpression` 的 BOOL | comfy-core 节点（工作流里 `193/194/195` 已经在用），`bool(result)` 输出。已在本机 simpleeval 验证 `a >= 3` 返回 Python bool | 若 RunningHub 版本过旧导致 BOOL 异常，把 8 个判断换成 8 个 `PrimitiveBoolean`，参数变 8 个 |
| `ref_image_7/8` 槽位 | 8/9 张变体需要 9 个槽位，序列化时追加在 inputs 末尾（和 ComfyUI 自己存 `ref_image_6` 的方式一致） | 先测 9 张，若 8/9 报参数缺失，说明前端重建了槽位，改用两段式（7 张 + 另接） |
| 成本 | `ref_image_size` 默认 `max`，每张图在每个采样步都参与计算，9 张会明显变慢 | 6 张以上把 `ref_image_size` 改成 `match` |
| 预校验 | 未启用的 LoadImage 不会执行，但平台可能对空字段做预校验 | 9 个 `image` 字段全传，多余的重复第 1 张（脚本已这么做） |

## 和 v1.6 的关系

v1.6 是 1~3 张版本（2 个布尔参数）。v1.7 覆盖了它的全部场景，参数从 2 个变成 1 个，**用 v1.7 即可**，v1.5 / v1.6 都没动。
